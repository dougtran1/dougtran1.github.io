The problem

Customers at physical card shops waste time digging through bulk boxes looking for specific cards. It takes up table space meant for tournaments and pushes sales toward online competitors like TCGPlayer. Shop owners lose foot traffic and revenue.

The pitch behind this build: a public inventory site that lets customers browse what the shop actually has, reserve cards online, and pick them up in store within a 48-hour hold window.

What I built

A full production-feature stack on free-tier services. Three card games supported (Pokemon, MTG, One Piece), customer accounts with wishlists and stock notifications, an admin panel for inventory + analytics, and an atomic hold system that prevents double-reservations.

  • Browse + filter by game, set, rarity, condition, price range
  • Reserve cards for in-store pickup with a 48-hour hold timer
  • Customer accounts — wishlist, order history, "notify me when in stock"
  • Admin panel — add cards via API search (PokeTCG, Scryfall), CSV bulk import, manual entry, dynamic pricing
  • Analytics dashboard — inventory value, popular cards, traffic, with role-based access
  • Light/dark mode, real-time stock notifications via WebSocket

Tech stack

Constraint: everything had to run on free tiers. The whole stack costs $0/month and still supports the full feature set.

How holds work

The hold system was the trickiest piece. If two customers click "reserve" on the same card at the same moment, only one should win. I used a Postgres transaction inside a Supabase RPC so the inventory check and hold insert happen atomically. A scheduled cron job clears expired holds back to available stock every 5 minutes.

customer clicks reserve ↓ RPC: lock row, check stock, insert hold (atomic) ↓ hold expires after 48h → cron releases stock ↓ pickup confirmed → hold marked complete

The admin side

Shop owners aren't going to manually type 500 cards into a database. The admin panel uses the PokeTCG and Scryfall APIs so a staff member can search "Charizard ex" and one click auto-fills the image, set, rarity, and current market price. Pricing supports either auto market price + markup percent or a manual override per card.

For bulk inventory adds (e.g. opening a new shop), a CSV import takes a spreadsheet of set codes and pulls everything from the APIs in one batch.

Database design

10 tables behind the scenes — cards, holds, users, wishlists, notifications, audit logs. Row-level security policies in Supabase enforce who can see what (customers only see their own holds; staff see everyone's; owners see analytics).

What's deliberately out of scope

No payments. Holds are reservation-only — pay in store. This was a feature, not a limitation: the goal is to drive foot traffic, not to compete with TCGPlayer's checkout. Skipping Stripe also kept the project on the free tier.

Phone-based card scanning (point camera at a card to add it) is a separate future project. Computer vision and a mobile app are out of scope for a website demo.

Outcome

Shipped end-to-end in two days. Lives at the live demo with three seeded accounts (owner, staff, customer) so anyone can poke around the full feature set without signing up.

The piece I'm proudest of: a feature-complete production app — auth, RLS, atomic transactions, real-time notifications, analytics, dynamic pricing — running on $0/month of infrastructure. It's the demo I show to small business owners to make the case that custom software is reachable for them.
